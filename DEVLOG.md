## 2026-06-09 · Fix notifications: switch Tauri app from osascript to tauri-plugin-notification

**What:** Replaced `osascript`-based notifications in the GUI app with `tauri-plugin-notification`. Root cause of the symptoms (no sound, no auto-banner, only visible after manually opening Notification Center): `osascript` is a child process — macOS attributes the notification to the `osascript` binary, not to `com.avr.claude-notify`. No user has ever granted notification permission to osascript in this context, so macOS silently drops banners and sound. Changes: (1) Added `tauri-plugin-notification = "2"` to `src-tauri/Cargo.toml`. (2) Registered the plugin in `main.rs`. (3) Added `notification:default` to capabilities. (4) Created `src-tauri/src/tauri_notifier.rs` with `TauriNotificationSender<R>` that calls `app.notification().builder().title(…).body(…).sound("Glass").show()` — under the hood the plugin calls `notify_rust::set_application("com.avr.claude-notify")` so macOS correctly attributes the notification. (5) Threaded a `sender: &dyn NotificationSender` parameter through `poll_instance` and `check_usage` in the core crate (previously hardcoded to `RealNotificationSender` which osascripts on macOS). CLI path (`run_monitor`) still creates its own `RealNotificationSender`. (6) Updated `get_usage` Tauri command to accept `AppHandle` and pass `TauriNotificationSender`. (7) Updated `test_notification` command to use the same path.

**Why choosing `tauri-plugin-notification` over calling `notify_rust::set_application` directly:** The plugin is the official Tauri-maintained path; it sets `set_application` to `com.avr.claude-notify` in production builds, handles the spawned-task requirement, and is already in the Tauri plugin ecosystem. The CLI daemon keeps `osascript` for now because a launchd service has no app bundle identity — that's a separate problem and minor compared to the GUI fix.

**Caveat — dev mode:** `tauri-plugin-notification` sets the app ID to `com.apple.Terminal` in dev builds (`tauri::is_dev() == true`). So `tauri dev` still shows notifications under Terminal. A production build (`cargo tauri build`) uses `com.avr.claude-notify` correctly. Users seeing no improvement should use the production build.

**Caveat — persistent/Alert style:** The config `notifications.persistent = true` option had no effect here: whether a notification stays until dismissed (Alert) vs auto-dismisses (Banner) is a per-app user setting in System Settings → Notifications → Claude Notify. The `Timeout` parameter is accepted but ignored by `TauriNotificationSender` since the plugin has no timeout knob.

## 2026-06-08 · Fix post-login 403 — wrong org selected, not bad cookies

**What:** New/re-logged-in accounts showed `auth required: HTTP 403 Forbidden — session expired or invalid` on the dashboard despite a successful login. The cookies were fine — the symptom was misleading. Login reaches the `auth-complete` success path (Chrome closes, main window shows) only *after* `fetch_org_id` succeeds and the session is saved, so the 403 came later, from the usage poll. Root cause: `fetch_org_id` took `orgs.first()` from `/api/organizations`. When an account has more than one org (personal + Team/Work, or an API-only org), `/organizations/{id}/usage` returns 403 for any org that isn't the chat-scoped one — while `/organizations` (the list) still returns 200, hence org-fetch "succeeds" but usage-fetch 403s with the same cookies. Reworked `fetch_org_id(cookie, preferred_org)` to pick the org the way the browser does: (1) the `lastActiveOrg` cookie UUID (now passed in from the captured session), (2) first org advertising a `chat` capability, (3) first org as fallback. Extracted the choice into a pure `select_org_id` helper with 5 unit tests.

**Why:** The old CLI never hit this because it scraped the org UUID by intercepting the real frontend's `/usage` call, so it always got the right org; the GUI's `orgs.first()` rewrite silently dropped that guarantee. `lastActiveOrg` is the most reliable signal because it's literally the value the chat frontend uses to build the usage URL; the capability filter is the fallback for when that cookie is absent/stale, and skips API-only orgs that are guaranteed to 403.
