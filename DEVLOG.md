## 2026-07-13 · Rebuild History → Resets around a corrected reset-detection heuristic

**What:** Reworked the Resets view in `ui/src/routes/History.svelte`. Root problem: reset detection used raw string inequality on `*_resets_at`, but the API reports each window's reset time as `now + remaining`, so the timestamp jitters by sub-second (sometimes whole-second) amounts on *every* poll. Over 20 days of real data this turned ~68 genuine 5h resets into **3,356 phantom ones** (and ~3 weekly resets into 4,050). The old scatter plot also put `usageAtReset` on the Y axis — which read the *new* window's ~0% usage, not anything meaningful. Fixes:
1. **`jumpedForward()` / `isWindowBoundary()` helpers** — a genuine reset is when `resets_at` jumps forward by > 30 min (real windows are hours apart; jitter is sub-minute). The reset scan also carries the last non-null `resets_at` across idle gaps so windows that reset while usage is 0/null are still caught. Validated on real data: 68/48 5h resets, 3/4 weekly — realistic.
2. Reused the same helper for the overview `windows` grouping (feeds the empirical prediction), the main chart's reset lines (was drawing thousands of dashed lines), and the "current 5h window" filter (was matching one exact jittered string, dropping most of the window).
3. **New `ResetEvent` model** — `{resetAt, detectedAt, windowType, peakPct, hitCap, lagMinutes}`. `peakPct` = peak usage in the window that *ended* (how hard it was hit before reset), replacing the meaningless new-window usage.
4. **Redesigned view**: four summary tiles (5h resets · maxed-out count · avg peak · weekly resets) + a day-grouped timeline where each row shows the clock time it reset, a peak-usage bar, the peak %, and a "maxed" flag; weekly (7d) resets render as distinct highlighted rows. Removed the scatter SVG, its tooltip/hover machinery, and the red anomaly badge.

**Why:** The page was "not clear" because it was showing thousands of fake resets against a meaningless axis. A user cares about *when* windows reset (rhythm), *how much* they'd used before each reset (peak — did they leave capacity or slam the cap), and *how often* they max out. The timeline answers all three directly.

**Rust side (same session):** Applied the identical fix to `summarize_windows` in `crates/claudar-core/src/history.rs` (feeds `predict_windows_remaining` / the CLI). Added `is_window_boundary()` + `parse_reset()` helpers mirroring the JS: a boundary is a forward jump > 30 min, a None↔Some transition, or — when a timestamp can't be parsed — string inequality (keeps the existing `"T1"`/`"T2"` label-based tests valid). Added a `summarize_ignores_subminute_reset_jitter` regression test. `cargo test -p claudar-core` green (98 pass); workspace `cargo check` clean.

## 2026-07-01 · Fix silent rekey on keychain failure + per-poll prompt storm

**What:** Reworked `crypto::get_or_create_key` (`crates/claudar-core/src/crypto.rs`). Two fixes:
1. **In-process key cache** (`OnceLock`). `SessionData::load` runs on every poll (`monitor.rs:217`), so the key was resolved — and the macOS keychain hit — every polling cycle, popping a permission prompt every few minutes. Now resolved at most once per process; only successful resolutions are cached, so a transient failure is retried next call.
2. **No silent rekey.** The old code treated *any* keychain error as "no key — generate one," so a single denied/locked read minted a fresh random `.master.key` that could no longer decrypt existing sessions (`aead::Error`). Split by build: debug builds (`debug_assertions`) skip the keychain entirely and use a stable on-disk key (unsigned dev binaries get a new code signature every rebuild, so macOS re-prompts forever and "Always Allow" never sticks). Release builds read the keychain and, on a read failure, only reuse an *existing* fallback file — never generate a new key on macOS. Headless-Linux (`NoStorageAccess`, no Secret Service) is the one platform allowed to create a first-run file key.

**Why:** A user hit `aead::Error` decrypting sessions plus a keychain prompt every 5 min. Root cause was the combination: keychain read failing (ACL invalidated by a binary-signature change) *and* code that responds to a read failure by silently swapping the encryption key. Only session cookies are encrypted, so the data itself is disposable (re-login), but silently destroying it and then prompt-storming the user is never acceptable. Built `Claudar_0.4.2_aarch64.dmg` (~6 MB) from the release path so the fix is installable.

**Caveats:** Still unsigned — for an unsigned/ad-hoc binary, keychain "Always Allow" may not durably stick, so release builds can still prompt ~once per launch (down from every poll); a stable Developer ID signature + notarization is the only robust fix and is out of scope here. macOS release now never creates an on-disk fallback key, so `NoStorageAccess`-classification only matters off-macOS. `cargo test -p claudar-core` green (97 pass); debug + release `cargo check` green; `cargo tauri build --config tauri.conf.ci.json` produced the aarch64 DMG end-to-end.

**What:** Rewrote the `prediction` estimator in `ui/src/routes/History.svelte`. Old logic averaged `seven_day_delta` only over windows that pegged ≥100% (`hit_100`), requiring ≥2 of them — so it almost always fell back to the theoretical rate (100/33.6 ≈ 2.98%) and showed "theoretical estimate" even with lots of history. New logic: `avgCost = Σ(positive 7-day rises) / Σ(window fullness = peak/100)` over every window with real usage, gated on `fullEquiv ≥ 3` full-window-equivalents and a sanity band `0.3 ≤ cost ≤ 15`, else theoretical. `windowsObserved` now reports rounded full-window-equivalents. **Why:** User reported a "negative per-window cost." Investigated (code read + ported the exact logic to a node script over the same synthetic data): the value is provably never negative — it's either the +2.98 theoretical or a mean of `max(0, …)`-clamped deltas. The "−" was a misread of the "·  ~" separator+tilde at low screenshot resolution; confirmed by extracting the rendered DOM text ("7-day: 92% · ~3.90% per window"). The real defect the screenshot exposed was the estimator defaulting to theoretical despite 25 windows of data. Chose a usage-weighted aggregate over per-window-then-average because the 7-day limit is a *rolling* window — individual window deltas are noisy and frequently ≤0 as old usage ages off; summing only positive rises and dividing by observed fullness gives the marginal cost of an additional full window (its own aging happens 7 days out, beyond the horizon to the cap), which is exactly what "windows remaining" needs. Verified on synthetic Heavy/Steady/Light: now empirical, 2.12–3.90%/window, windows-remaining 2.0/9.1/24.6.

**Caveats:** Empirical cost depends on poll density and on `seven_day_resets_at`/usage being monotone-ish within a window; the sanity band guards degenerate spikes. No backend change. `npm run build` clean (lone pre-existing Wizard.svelte warning).

## 2026-06-10 · Encrypt session files at rest (AES-256-GCM + OS keychain)

**What:** Added `crates/claudar-core/src/crypto.rs` and wired it into `SessionData::save`/`load` (`storage.rs`). Session files (`~/.config/claudar/sessions/{instance}.json`) — which hold `session_key`, `cf_clearance`, and the full cookie string — are now AES-256-GCM encrypted on disk as a versioned envelope (`{version, nonce, ciphertext}`) and chmod'd `0600`. Old plaintext session files are detected on load, parsed as before, then immediately re-saved encrypted (transparent migration, no re-login needed). New deps: `keyring` (with `apple-native`, `windows-native`, `sync-secret-service`, `crypto-rust` features), `aes-gcm`, `base64`.

**Why:** A leaked session file = full Claude.ai account impersonation, and it sat as plaintext JSON. Considered three approaches: (1) **OS-keychain-backed AES key (chosen)** — both the macOS LaunchAgent and Linux `systemd --user` service run in the user's session, so Keychain/Secret Service access works silently with no extra prompts during normal operation. (2) **Passphrase-derived vault** — rejected: the unattended polling daemon couldn't decrypt after a reboot without the user re-entering a password, defeating the "background monitor" use case. For the keychain-unavailable fallback (headless Linux with no Secret Service), considered a random key file (chosen) vs. deriving the key from a hardcoded string + stable machine values (rejected — source is public on GitHub, so anything derivable from public env values gives an attacker with file access the key for free; a random key in a separate `0600` file has real entropy). Machine-ID binding on top of the random key was also considered and rejected to keep it simple.

**Caveats:** `cargo test` skips the keychain entirely (`cfg(not(test))`) and always uses the fallback file, so test runs never prompt for Keychain access. On macOS, ad-hoc-signed dev builds change binary signature on every `cargo build`, which can trigger repeated Keychain "Allow access" prompts in development — not an issue for signed release builds. Verified end-to-end manually: migration of a real plaintext session file worked, the key landed in the macOS Keychain (not the fallback file), and the session file came out `-rw-------`.

## 2026-06-08 · Fix post-login 403 — wrong org selected, not bad cookies

**What:** New/re-logged-in accounts showed `auth required: HTTP 403 Forbidden — session expired or invalid` on the dashboard despite a successful login. **Why:** The old CLI never hit this because it scraped the org UUID by intercepting the real frontend's `/usage` call, so it always got the right org; the GUI's `orgs.first()` rewrite silently dropped that guarantee. `lastActiveOrg` is the most reliable signal because it's literally the value the chat frontend uses to build the usage URL; the capability filter is the fallback for when that cookie is absent/stale, and skips API-only orgs that are guaranteed to 403.

JSON round-tripping (`JSON.parse(JSON.stringify(config))`) was needed instead of `structuredClone` to clone the config before mutating — Svelte 5 `$state` wraps objects in `Proxy`, which `structuredClone` cannot serialize (`DataCloneError`); this surfaced as a real runtime bug during verification (every `set_config` call in Settings was silently failing).

**Note:** Visual verification again couldn't use `screencapture`/Accessibility (same sandboxed-agent TCC limitation as Phase 5 — confirmed black frames and zero enumerable windows). Screenshots of all three screens plus the add/remove modals confirmed correct rendering, and the invoke log confirmed `set_config`/`set_autostart`/`add_instance`/`remove_instance` fire with correctly-shaped payloads. `cargo build`/`cargo test --workspace` (70 passing) and `npm run build` also pass.

## 2026-06-07 · Phase 3 — Monitor loop + event bus embedded in Tauri

**What:** Wired the monitoring daemon into the Tauri process. `src-tauri/src/monitor_loop.rs` spawns one tokio task per configured instance (via `tauri::async_runtime::spawn`).
